\subsection{Functional Requirements}

\textbf{Sign up \& Login}
\begin{description}
    \item[\textbf{[R1]}] The platform shall allow new users to register an account by providing personal information.
    \item[\textbf{[R2]}] The platform shall allow registered users to log in by entering their registered email and password.
\end{description}

\noindent
\textbf{Map Explorer}
\begin{description}
    \item[\textbf{[R3]}] The platform shall display an interactive map centered on the user's current location.
    \item[\textbf{[R4]}] The platform shall allow users to input an "Origin" and "Destination" of the desired path.
    \item[\textbf{[R5]}] The platform shall allow users to swap the origin and destination inputs.
    \item[\textbf{[R6]}] The platform shall calculate and display the top 5 paths options ranked by score.
    \item[\textbf{[R7]}] The platform shall visualize the geometry, obstacles and scores of the top 5 paths on the map.
    \item[\textbf{[R8]}] When the origin coincides with the current location, the platform shall allow users to start the navigation mode for the currently selected path.
    \item[\textbf{[R9]}] When the navigation is started, the platform shall visualize the user's position in real-time.
    \item[\textbf{[R10]}] When the navigation is started, the platform shall display a dynamic navigation overlay providing the name of the street being traversed and the estimated speed.

    \item[\textbf{[R11]}] The platform shall allow users to interrupt the active navigation mode at any time.

    \item[\textbf{[R12]}]  When the navigation is completed, the platform shall present to registered users a summary screen containing statistics and the map of the path taken.

    \item[\textbf{[R13]}] When the navigation is completed, the platform shall allow registered users to modify the path status and the obstacles.
\end{description}

\noindent
\textbf{Active Path Recording}
\begin{description}
    \item[\textbf{[R14]}] The platform shall allow registered users to start an active recording session.
    \item[\textbf{[R15]}] The platform shall utilize device sensors to automatically detect obstacles.
    \item[\textbf{[R16]}] The platform shall display real-time metrics during the trip, including duration, current speed and distance traveled.

    \item[\textbf{[R17]}] The platform shall allow registered users to stop the recording and immediately transition to the summary screen to review the captured data.

    \item[\textbf{[R18]}] The platform shall allow registered users to modify status and obstacles in the captured data summary.

    \item[\textbf{[R19]}] The platform shall allow registered users to publish the captured path along with its data.
\end{description}

\newpage
\noindent
\textbf{Manual Path Creation}
\begin{description}
    \item[\textbf{[R20]}] The platform shall allow registered users to manually draw the path on the map.
    \item[\textbf{[R21]}] The platform shall allow registered users to manually place obstacle markers along the drawn path.
    \item[\textbf{[R22]}] The platform shall allow registered users to set the status of the drawn path.
    \item[\textbf{[R23]}] The platform shall allow registered users to publish the drawn path along with its data.
\end{description}

\noindent
\textbf{Trips \& Published Paths}
\begin{description}
    \item[\textbf{[R24]}] The platform shall display a dashboard listing the user's historical trips and their data, sorted chronologically.
    \item[\textbf{[R25]}] The platform shall allow registered users to view a list of paths published by them.
    \item[\textbf{[R26]}] The platform shall allow registered users to delete any of their published paths.
\end{description}

\noindent
\textbf{User Profile}
\begin{description}
    \item[\textbf{[R27]}] The platform shall display a user profile screen summarizing the main aggregate statistics.
\end{description}

\subsubsection{Sequence Diagrams}
The functions used in the sequence diagrams follow these conventional meanings:
\begin{itemize}
    \item \textbf{press(Button)}: Represents the action of a user pressing Button.
    \item \textbf{submit(Content)}: Indicates a user uploading Content to the platform.
    \item \textbf{showPage(Page)}: Displays the content of a specific Page.
    \item \textbf{showError(Error)}: Displays an error message indicating an issue that occurred.
    \item \textbf{check()}: Verifies the validity of the information provided by the user.
    \item \textbf{send(ConfirmationEmail)}: The system sends a confirmation email to user.
    \item \textbf{confirmEmail()}: The user confirms the email, which triggers a confirmation signal to the system.
    \item \textbf{register(User)}: The system registers the user.
    \item \textbf{update(Data)}: Refers to internal processes that update database records with Data.
    \item \textbf{enter()}: Represents the action of a user entering an input.

\subsection{Performance Requirements}

Given the application's focus on real-time navigation and outdoor activities, efficient resource usage and low latency are essential to ensure safety and usability. To ensure an optimal User experience:

\begin{itemize}
    \item The system shall update real-time dashboard metrics (Speed, Distance, Obstacles) within 1 second of receiving data from the device sensors;
    \item The system shall respond to general User interface requests within 2 seconds under normal load conditions;
    \item The system shall support at least 10,000 concurrent Users navigating or recording simultaneously;
    \item Database queries shall be completed within 1.5 seconds;
    \item The system shall be capable of processing and saving trip summaries for at least 100 Users per second during peak hours;
    \item The Path Calculation process (Top 5 options) shall be completed and displayed to the User within 3 seconds under normal load conditions;
    \item The application shall not consume more than 15\% of the battery capacity per hour on a standard reference device while in "Active Navigation" mode (screen on and GPS tracking enabled), to prevent battery drainage during long rides.
\end{itemize}

\subsection{Design Constraints}
This section explain the different constraints that the platform must respect such as the standard compliance for the data protection and hardware limitations.

\subsubsection{Standards Compliance}

The Platform operates at the intersection of sensitive user data processing and third-party proprietary services. Specifically, the system must handle Personally Identifiable Information (PII) and continuous geolocation history, which constitutes a significant privacy risk as it can reveal user habits and private locations. Consequently, the architecture must be designed to strictly comply with the General Data Protection Regulation (GDPR) and potentially the California Consumer Privacy Act (CCPA), embedding privacy-by-design principles directly into the software core. Simultaneously, the dependency on external map providers (e.g., OpenStreetMap or Google Maps) mandates rigorous adherence to their Terms of Service, requiring the software to dynamically display proper copyright attributions and strictly enforce technical limitations on offline data caching. The system must therefore be architected with the flexibility to adapt to this dual set of regulatory and licensing constraints, ensuring compliance without compromising functionality.

\subsubsection{Hardware Limitations}
The mobile application client relies strictly on the availability and precision of consumer-grade hardware sensors to execute its core logic. Specifically, the host device must be equipped with a GPS, an accelerometer, and a gyroscope, as the automatic detection of path obstacles and accurate real-time navigation are algorithmically dependent on the continuous data stream provided by this specific sensor suite. Furthermore, considering the prolonged nature of cycling activities, the application architecture must operate within the strict energy and thermal constraints of standard smartphones, ensuring that continuous background tracking does not deplete the battery before the trip concludes or trigger thermal throttling that would degrade system performance.

\subsection{Software System Attributes}
This section explains the design constraints that the platform must respect, covering both regulatory compliance for data protection and specific hardware limitations.

\subsubsection{Reliability \& Availability}
The system is designed to ensure high availability for Users, targeting an uptime of 99.9\%. To achieve this, the platform relies on redundant cloud infrastructure to minimize the risk of service interruptions. Furthermore, the mobile application is designed to be resilient to network failures; it utilizes local caching mechanisms to ensure that critical features, such as path recording, remain functional and no data is lost even when the device temporarily loses connectivity to the server.

\subsubsection{Security}
The system handles highly sensitive information, including real-time geolocation history and personal user profiles. Consequently, these data must be protected with strong encryption algorithms (at rest), and data in transit must always be encrypted via HTTPS to ensure security against interception. The system may be particularly susceptible to API abuse and unauthorized access attempts; hence, it should incorporate robust authentication measures (such as token-based access) and rate-limiting strategies to prevent or reduce the impact of such attacks.

\subsubsection{Maintainability}
The backend components should be designed to be easily scalable, maintainable, reusable, and testable to handle a growing number of cyclists and tracks. To achieve this, the system should implement well-defined architecture that allows for easy updates and modifications both on the front and the back end. The code should be readable and fully documented. \subsubsection{Portability}
As a mobile-centric platform, the client application must be compatible with the major mobile operating systems, specifically Android and iOS. It should efficiently utilize native hardware features (such as GPS and accelerometers) while ensuring a consistent user experience. Moreover, the interface should be optimized for use on various device form factors, ensuring flexibility and usability across both standard smartphones and larger tablets used for path planning.
